# Анализ производительности object_detector

## Дата анализа
24 января 2026

## Текущее состояние архитектуры

### Структура object_detector

#### Базовые классы
- `ObjectDetectorBase` - базовый класс детектора
- `ModelBasedDetectorBase` - базовый класс для модельных детекторов (YOLO, RTDETR, RFDETR)
- Конкретные детекторы: `ObjectDetectorYolo`, `ObjectDetectorYoloMp`, `ObjectDetectorRtdetr`, `ObjectDetectorRfdetr`

#### Detection Threads
Каждый детектор создает несколько потоков детекции (`num_detection_threads`, по умолчанию 3):
- `DetectionThreadYolo` - модели в потоках (threading)
- `DetectionThreadYoloMp` - модели в процессах (multiprocessing)
- `DetectionThreadRtdetr` - RT-DETR модели
- `DetectionThreadRfdetr` - RF-DETR модели

#### Распределение нагрузки
- Round-robin распределение кадров между detection threads через `thread_counter`
- Каждый поток имеет свою очередь (`queue_in`) размером `DEFAULT_THREAD_QUEUE_SIZE = 2`

### Реализация ultralytics

#### DetectionThreadYolo (threading)
- Модель загружается в потоке через `init_detection_implementation()`
- Модель создается: `self.model = YOLO(self.model_name)`
- Оптимизации:
  - `model.fuse()` - слияние Conv+BN слоев (опционально)
  - `model.half()` - половинная точность (если `half=True`)
- Инференс: `model.predict(source=valid_images, classes=..., verbose=False, **inf_params)`

#### DetectionThreadYoloMp (multiprocessing)
- Использует `MpControl` для управления процессами
- `MpControl.start()` создает отдельные процессы через `mp.Process(target=worker)`
- **Каждая модель загружается в своем процессе** через `MpWorkerYolo.init_worker()`
- Это правильная практика использования ultralytics - изоляция процессов предотвращает конфликты GIL и проблем с памятью
- Коммуникация через `mp.Queue` (input_queue, output_queue)

#### Важно
✅ **Модели правильно порождаются каждая в своем процессе** - это соответствует лучшим практикам ultralytics
- Не пытаться переиспользовать одну модель между процессами
- При оптимизации не нарушать изоляцию процессов

## Параметры производительности

### Текущие значения
- `DEFAULT_NUM_DETECTION_THREADS = 3` - количество потоков детекции
- `DEFAULT_INPUT_QUEUE_SIZE = 10` - размер входной очереди детектора
- `DEFAULT_THREAD_QUEUE_SIZE = 2` - размер очереди каждого потока
- `DEFAULT_INFERENCE_SIZE = 640` - размер изображения для инференса
- `DEFAULT_CONFIDENCE = 0.25` - порог уверенности
- `PROCESSING_SLEEP_INTERVAL = 0.01` - интервал ожидания в циклах обработки (10ms)

### Параметры инференса (InferenceParams)
- `imgsz: int = 640` - размер изображения
- `device: Optional[str] = None` - устройство (auto-detect)
- `half: bool = True` - половинная точность (FP16)
- `conf: float = 0.25` - порог уверенности

## Узкие места производительности

### 1. Размеры очередей
**Проблема**: Маленькие размеры очередей могут приводить к потере кадров
- `DEFAULT_INPUT_QUEUE_SIZE = 10` - может быть недостаточно при высокой нагрузке
- `DEFAULT_THREAD_QUEUE_SIZE = 2` - очень маленький размер, кадры теряются при переполнении

**Симптомы**:
- Логи: "Failed to put image ... to ObjectDetection queue. Queue is full."
- Логи: "Output queue full, dropping detection result"
- Потеря кадров через `queue_dropped_id`

**Влияние**: При высокой частоте кадров (30 FPS) и медленном инференсе очереди переполняются

### 2. Round-robin распределение
**Текущая реализация**: Простое циклическое распределение через `thread_counter`
```python
res, dropped_id = self.detection_threads[self.thread_counter].put(image, force=True)
self.thread_counter += 1
if self.thread_counter >= self.num_detection_threads:
    self.thread_counter = 0
```

**Проблема**: Не учитывает загрузку потоков
- Если один поток медленнее, он все равно получает равную долю кадров
- Может приводить к накоплению кадров в медленном потоке

**Влияние**: Неравномерная загрузка потоков, потенциальные узкие места

### 3. Обработка ROI
**Текущая реализация**: Обрезка изображений в `utils.create_roi()` для каждого кадра
```python
split_image = utils.create_roi(image, coords)
```

**Накладные расходы**:
- Копирование данных изображения для каждого ROI
- Множественные вызовы `img[y:y+h, x:x+w]` создают новые массивы
- При нескольких ROI на кадр - несколько копий

**Влияние**: Дополнительное использование памяти и CPU на обрезку

### 4. Stride обработка
**Текущая реализация**: Пропуск кадров через счетчик `stride_cnt`
- По умолчанию `vid_stride = 1` (обрабатываются все кадры)
- При `vid_stride > 1` кадры пропускаются

**Влияние**: Снижает нагрузку, но может пропускать важные события

### 5. Копирование данных между процессами (yolo_mp)
**Текущая реализация**: 
- Изображения передаются через `mp.Queue` между процессами
- Результаты копируются обратно: `cpu_results.append(res.cpu())`

**Накладные расходы**:
- Сериализация/десериализация numpy массивов
- Копирование данных изображений между процессами
- Дополнительное использование памяти

**Влияние**: Задержка и использование памяти при multiprocessing

### 6. Отсутствие батчинга
**Текущая реализация**: Каждый кадр обрабатывается отдельно
- `model.predict(source=valid_images, ...)` - может принимать список, но обрабатывает последовательно
- Ultralytics автоматически батчит внутри, но мы не контролируем размер батча

**Влияние**: Неоптимальное использование GPU при малых батчах

## Возможности оптимизации

### 1. Увеличение размеров очередей
**Рекомендация**: Увеличить размеры очередей для буферизации
- `DEFAULT_INPUT_QUEUE_SIZE`: 10 → 30-50 (зависит от FPS и времени инференса)
- `DEFAULT_THREAD_QUEUE_SIZE`: 2 → 5-10

**Оценка эффекта**: Снижение потерь кадров на 70-90%

**Риски**: Увеличение использования памяти

### 2. Умное распределение нагрузки
**Рекомендация**: Распределение на основе загрузки очередей
- Вместо round-robin проверять `queue_in.qsize()` каждого потока
- Отправлять кадр в поток с наименьшей загрузкой

**Оценка эффекта**: Улучшение балансировки нагрузки на 20-30%

**Сложность**: Средняя (нужно добавить мониторинг очередей)

### 3. Оптимизация ROI обработки
**Рекомендация**: 
- Кэширование ROI координат (уже есть `_roi_cache`)
- Предварительная обрезка на этапе захвата (если возможно)
- Использование views вместо копий где возможно

**Оценка эффекта**: Снижение CPU на 10-15% для сценариев с ROI

**Сложность**: Средняя

### 4. Настройка параметров инференса
**Рекомендация**: Тонкая настройка параметров
- `imgsz`: Оптимизировать под разрешение источников (не всегда 640)
- `half=True`: Уже используется, хорошо
- `device`: Явно указывать GPU если доступен
- `conf`: Настраивать под задачу (баланс точность/производительность)

**Оценка эффекта**: Улучшение производительности на 15-25%

**Сложность**: Низкая (конфигурация)

### 5. Батчинг изображений
**Рекомендация**: Накапливать несколько кадров перед инференсом
- Собирать батч из нескольких кадров из очереди
- Передавать батч в модель одним вызовом
- Ultralytics поддерживает батчинг автоматически

**Оценка эффекта**: Улучшение GPU utilization на 20-40%

**Сложность**: Высокая (нужно изменить логику обработки)

**Риски**: Увеличение задержки (latency)

### 6. Мониторинг производительности
**Рекомендация**: Добавить метрики
- Время инференса на кадр
- Размеры очередей
- Количество потерянных кадров
- Использование памяти моделями
- FPS детекции

**Оценка эффекта**: Позволит выявить узкие места в реальном времени

**Сложность**: Средняя

### 7. Оптимизация копирования данных (yolo_mp)
**Рекомендация**: 
- Использовать shared memory где возможно
- Минимизировать копирование (передавать только необходимые данные)
- Оптимизировать сериализацию numpy массивов

**Оценка эффекта**: Снижение задержки на 10-20% для multiprocessing

**Сложность**: Высокая

## Метрики для мониторинга

1. **Время инференса**: время обработки одного кадра моделью (мс)
2. **Пропускная способность**: кадров в секунду (FPS)
3. **Задержка**: время от захвата кадра до получения результата (мс)
4. **Использование памяти**: память на модель, очереди, изображения (MB)
5. **Загрузка CPU/GPU**: распределение нагрузки между потоками/процессами (%)
6. **Потери кадров**: количество кадров, потерянных из-за переполнения очередей
7. **Размеры очередей**: текущие размеры всех очередей

## Рекомендации по использованию

### Для высокой производительности
- Использовать `DetectionThreadYoloMp` (multiprocessing) для лучшей изоляции
- Увеличить `num_detection_threads` до 4-6 (зависит от CPU/GPU)
- Увеличить размеры очередей
- Настроить `imgsz` под разрешение источников
- Использовать GPU (`device='cuda'`)

### Для низкой задержки
- Использовать `DetectionThreadYolo` (threading) - меньше overhead
- Уменьшить `num_detection_threads` до 1-2
- Уменьшить размеры очередей (меньше буферизация)
- `vid_stride = 1` (обрабатывать все кадры)

### Для экономии ресурсов
- Увеличить `vid_stride` (пропускать кадры)
- Уменьшить `imgsz` (меньше разрешение)
- Использовать меньшую модель (yolov8n вместо yolov8s/m/l)
- Уменьшить `num_detection_threads`
