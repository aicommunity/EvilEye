# GUI Fixcheck Summary (2026-04-15)

## Контекст

Цель серии `fixcheck` — проверить, ушли ли падения с `exit 137` после изменений в shutdown/lifecycle, и сравнить производительность в GUI-режиме между baseline и безопасным MP-профилем (`*_mp_safe30`).

Использованные прогоны:

- `poly-videos` GUI 30s:
  - baseline: `logs/diagnostics/poly-videos_baseline_gui_fixcheck_30s.log`
  - safe MP: `logs/diagnostics/poly-videos_mp_safe30_gui_fixcheck_30s.log`
  - KPI: `reports/poly-videos_gui_fixcheck_30s_kpi.md`
- `poly-videos-gst` GUI 45s (корректная сопоставимая пара):
  - baseline: `logs/diagnostics/poly-videos-gst_baseline_gui_fixcheck_bench45.log`
  - safe MP: `logs/diagnostics/poly-videos-gst_mp_safe30_gui_fixcheck_bench45.log`
  - KPI: `reports/poly-videos-gst_gui_fixcheck_bench45_kpi.md`

## Стабильность

- В серии `fixcheck` не зафиксированы `Traceback`, `ERROR`, `Killed`, `exit 137`.
- `Stop timeouts` и `Force-kills`: `0` в сравниваемых парах.
- После прогонов не осталось фоновых `evileye`-процессов.

Вывод: изменения по медленному/отложенному shutdown сработали в целевом сценарии GUI-бенчей.

Короткая интерпретация:

- По `p95` (задержка) меньше — лучше: в обеих парах выигрывает режим с MP.
- По `Hz` (пропускная способность) больше — лучше: в обеих парах выигрывает режим с MP.
- По `Max RSS` (пик RAM) меньше — лучше: особенно большой выигрыш с MP в `poly-videos-gst`.

## Практические выводы

1. Для GUI на текущем хосте безопасный MP-профиль (`*_mp_safe30`) показывает лучшую устойчивость.
2. По `poly-videos-gst` safe MP заметно выигрывает и по latency (`p95`), и по throughput (`Hz`), и по memory footprint (`Max RSS`).
3. Для регрессионных GUI-прогонов имеет смысл оставить увеличенный grace shutdown и профиль `safe30` как дефолт для стресс-проверок.

## Глоссарий метрик и аббревиатур

- **KPI** (*Key Performance Indicator*) — ключевой измеримый показатель качества/производительности.
- **RSS** (*Resident Set Size*) — объем физической RAM, реально занятой процессом в данный момент.
  - В отчетах `Max RSS` — максимальное зафиксированное значение RSS за прогон.
  - Важно: RSS не равен «всей памяти приложения» в широком смысле, но хорошо отражает реальное давление на RAM.
- **p95** (*95th percentile*) — 95-й перцентиль метрики.
  - Для `p95 Pipeline loop (ms)` это значение, ниже которого находится 95% итераций pipeline.
  - Чем ниже, тем стабильнее и быстрее обработка в «хвосте» задержек.
- **Hz** (*Hertz*) — частота циклов в секунду.
  - `Estimated pipeline Hz` — оценка пропускной способности pipeline (итераций/сек).
  - Чем выше, тем больше обработанных циклов за единицу времени.
- **ms** (*milliseconds*) — миллисекунды (`1/1000` секунды).
- **MB** (*megabytes*) — мегабайты.
- **Traceback** — стек исключения Python (признак аварийного пути выполнения).
- **Stop timeout** — модуль/компонент не завершился за отведенное время на остановку.
- **Force-kill** — принудительное завершение процесса (`SIGKILL`) после неуспешного graceful shutdown.
- **Baseline** — исходная (референсная) конфигурация для сравнения.
- **Candidate** — тестируемый вариант (в этих сравнениях: `*_mp_safe30`).
- **GUI** (*Graphical User Interface*) — графический интерфейс приложения.
- **MP** (*Multiprocessing*) — многопроцессный режим выполнения.
- **Safe MP (`safe30`)** — облегченный MP-профиль для стабильных коротких бенчей (с ограничением числа тяжелых process-компонентов).
