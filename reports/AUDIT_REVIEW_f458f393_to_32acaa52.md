## 1. Вывод

**Исходный аудит в основном адекватен коду `f458f393`: перечисленные проблемные ветви действительно существовали, а последовательность «контроль доступа и достоверные проверки → корректность → измерения и оптимизация → рефакторинг» разумна. Однако это был аудит web/API-контура с ограниченной динамической проверкой, а его план не обеспечивал полного закрытия рисков.**

**Реализация на `32acaa52` существенно продвинула исправления, но весь план считать выполненным нельзя.** Исправлены выдача чужого fallback snapshot, исходная семантика пустой WS-подписки, коллизия кадров разных run, секундная коллизия metadata, ложный exit 0 pytest и сборка SPA. Lazy routes действительно уменьшают стартовый JavaScript. Вместе с этим:

- остаются воспроизводимые обходы доступа к видео/метаданным;
- конкурентная сборка events может вернуть данные другой камеры;
- исправление покрытия detection-index внесло регрессию: существующие камеры больше не обновляются при изменении исходных данных;
- новый cache eviction уничтожает резервные ответы;
- семь API-тестов сломаны переносом кэша в отдельный модуль;
- браузерные лаги и устойчивость под нагрузкой не подтверждены измерениями до/после.

Новый подробный реестр и план: [`PROJECT_REAUDIT_32acaa52.md`](PROJECT_REAUDIT_32acaa52.md). Идентификаторы `R01`–`R17` далее относятся к нему.

## 2. Метод и пределы доказательности

Проверены исходный текст аудита, история и суммарный diff всех 29 коммитов, изменённые исходники и вызываемые ими сервисы, тесты, workflow, скрипты проверок, отчёты производительности и документация. Исторические ветви проверялись через `git show f458f393:<path>`; полный сервер старой ревизии не разворачивался. Для текущей ревизии выполнены API unit tests, frontend tests, typecheck, отдельная Vite-сборка и изолированные воспроизведения.

Уровни доказательств:

- **HTTP** — запрос к настоящему FastAPI-приложению с синтетическими пользователями и файлами, включая действующую аутентификацию;
- **функциональный эксперимент** — настоящая проблемная функция с контролируемыми файловой системой, источником данных или синхронизацией потоков;
- **статический вывод** — установленный путь исполнения по коду; пользовательский эффект в браузере/нагрузке отдельно не замерен;
- **гипотеза производительности** — необходимо измерение на репрезентативном стенде.

Новые воспроизведения не используют реальные камеры, пользовательский архив или внешний работающий сервис. Полные pipeline/GPU/Qt/PostgreSQL, Linux deployment, WAN и браузерные traces в этой проверке не прогонялись. Вывод «вся система исправна» из выполненных проверок не следует.

### B01–B07 и последовательность работ

Все семь исходных направлений оптимизации имеют основания в коде. Корректно, что отчёт отделял их от замеренных задержек и предлагал сначала baseline. При этом:

1. **B01:** видимость должна различать «observer ещё не сообщил», «видимых камер ноль» и скрытую вкладку.
2. **B02:** более узкий ответ не означает более узкий дисковый scan. Требовались раздельные метрики server scan, response bytes, parse/merge и первого маркера.
3. **B03:** ограничение параллелизма должно сопровождаться справедливым обслуживанием всех камер; один общий deadline на последовательный проход может навсегда исключать хвост списка.
4. **B04:** защищать нужно все state transitions — success, error, loading, cache writes, unmount, смену пользователя; не только поздний успешный ответ.
5. **B05:** частые React commits — правдоподобная причина нагрузки, но без Profiler невозможно установить её вклад. Throttle и перенос playhead в DOM требуют проверки плавности seek и синхронизации видео.
6. **B06:** освобождать слот по завершении worker правильно, однако deadline должен включать очередь. Ограничение работающих потоков не равно ограничению ожидающих задач.
7. **B07:** lazy routing разумен и ниже по приоритету. Размер entry chunk не равен времени до рабочего экрана: нужны route chunks и браузерный сценарий.

### Ограничения самого исходного аудита

- Результат назывался аудитом проекта, но глубина проверки была сосредоточена на web/API. Отсутствие находок в захвате, инференсе, записи или БД не означает отсутствия дефектов там.
- «Подтверждённые дефекты» в одной таблице объединяли прямое воспроизведение и статический анализ. Уровень доказательства стоило указать у каждого пункта.
- P0 объединял утечки и недостоверность CI. Это допустимый порядок блокировки выпуска, но не единая шкала тяжести пользовательского ущерба.
- Приёмка в основном проверяла последовательные happy-path сценарии. Не хватало конкурентности, смены источников, больших архивов, пустых камер, отмены, отзыва прав и общего бюджета ресурсов.
- Предложение выделить общий media ACL следовало выполнить в составе исправления доступа, включая journal routes; откладывание его охвата до косметического рефакторинга оставляло пробел.

**Итог:** исходный документ пригоден как список первичных дефектов и направлений, но недостаточен как законченная спецификация исправления и критерий допуска релиза.

## 7. Проверка заявлений о производительности

`audit_perf_baseline_2026-09-23.md` честно назван структурным, неизмеренным baseline. `audit_perf_measured_2026-09-23.md` содержит замеры локального сервера на пяти камерах, по 11 повторов с прогревом. Это полезная предварительная диагностика, но называть её gate завершения этапа 2 преждевременно.

Причины:

1. Raw JSON лежал в `/tmp` внешнего хоста и не приложен к Git; точные SHA до/после, аппаратная конфигурация и фиксированный архив отсутствуют.
2. Нет обязательных сценариев 1/4/16 камер, controlled cold/warm, WAN, WS `bytes_sent`, 10-минутного браузерного профиля и устойчивости памяти.
3. До/после различается объём detections — 3,94 → примерно 4,2 MiB; данные текущего дня изменяются. Такое сравнение смешивает эффект кода с ростом архива.
4. Таблица даёт timeline p95 292 мс, пояснение — около 145 мс; events 62 и 57 мс. После изменений detections p95 793 → 849 мс, events 62 → 316 мс. Без повторов и raw samples это не доказательство ни общего ускорения, ни устойчивой регрессии.
5. `scripts/audit_perf_probe.py:240` ожидает массив в `by_camera[Cam]`, хотя endpoint возвращает объект с полем `segments`. Доступ `segs[0]` приводит к ошибке, media benchmark не выполняется для нормального ответа. Range-сценарий не реализован.
6. Параметр `limit=500` у detections endpoint не объявлен и игнорируется; `ticks_only=true`, применяемый для маркеров UI, отсутствует. Четырёхмегабайтный ответ не представляет штатный запрос compact ticks.
7. Диагностические URL в probe не совпадают с текущим `/ready`; функция `state_thread_stats()` вообще не подключена к ответу diagnostics. Утверждение об отсутствии роста counters данным harness не обосновано.
8. Агрегаты включают ошибки HTTP без обязательного провала запуска; percentile по 11 ответам плохо характеризует редкие зависания. Исходные длительности каждого запроса не сохраняются.

**Допустимый вывод:** bundle стал меньше, отдельные API-замеры выполнены, добавлены механизмы снижения нагрузки. **Недоказанный вывод:** устранены web-ui тормоза и выполнены все критерии этапа 2.

## 8. Решение по приёмке

1. Принять локальные исправления A02/A05/A11/A14 и уменьшение entry bundle; сохранить их тесты и поведение.
2. Вернуть на доработку ACL media/events, индексирование, stale/cache и ресурсные ограничения согласно R01–R07.
3. Восстановить API gate и добавить интеграционные проверки transport/hooks, затем повторить измерения по новому плану.
4. Статусы «complete matrix», «Stage 2 gate» и «полностью выполнено» заменить на конкретный объём проверенного, пока критерии не выполнены.
