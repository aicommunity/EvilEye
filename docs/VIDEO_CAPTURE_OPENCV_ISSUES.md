# Известные проблемы с VideoCaptureOpencv и варианты решения

## Проблема

При использовании модуля `VideoCaptureOpencv` для захвата видеофайлов с включенным цикличным воспроизведением (`loop_play=True`) возникают критические проблемы стабильности:

### Симптомы

1. **Зависание `cv2.VideoCapture.read()`**
   - Метод `cv2.VideoCapture.read()` блокируется на неопределенное время
   - Поток `_retrieve_frames` останавливается, кадры перестают поступать в конвейер обработки
   - Контроллер сообщает "Collected 0 frames for processing"

2. **Краш FFmpeg/OpenCV**
   - Система завершается с кодом `134` (SIGABRT)
   - В логах появляется сообщение: `Assertion fctx->async_lock failed`
   - Указывает на проблемы конкурентного доступа в FFmpeg при многопоточном использовании

3. **Постоянные реконнекты**
   - Watchdog механизм обнаруживает отсутствие кадров и инициирует `reset_impl()`
   - Реконнекты происходят постоянно, но не решают проблему
   - Видео не воспроизводится стабильно

### Корневая причина

Проблема связана с фундаментальными ограничениями `cv2.VideoCapture` при работе с циклическими видеофайлами в многопоточной среде Python:

1. **Блокирующие операции**: `cv2.VideoCapture.read()` может блокироваться на уровне FFmpeg без возможности прерывания из Python
2. **Проблемы с seek**: Операция `cv2.CAP_PROP_POS_FRAMES` при достижении конца файла может вызывать внутренние состояния гонки в FFmpeg
3. **Многопоточность**: Использование `cv2.VideoCapture` из нескольких потоков (`_grab_frames`, `_retrieve_frames`) создает условия для deadlock в FFmpeg
4. **Отсутствие таймаутов**: OpenCV не предоставляет надежного механизма таймаутов для операций чтения

### Реализованные попытки решения

Были предприняты следующие попытки исправления:

1. **Watchdog механизм** (`_grab_frames` для VideoFile)
   - Мониторинг `last_frame_time` и инициирование `reset_impl()` при отсутствии кадров
   - **Результат**: Не решает проблему блокировки `read()`

2. **ThreadPoolExecutor с таймаутом**
   - Обертка `self.capture.read()` в `ThreadPoolExecutor` с `timeout=1.0`
   - **Результат**: Частично помогает, но не предотвращает краши FFmpeg

3. **Оптимизация seek для loop_play**
   - Использование `cv2.CAP_PROP_POS_FRAMES` вместо полного `reset()` при достижении конца файла
   - **Результат**: Улучшает производительность, но не решает проблему блокировок

## Варианты решения

### Вариант 1: Использование GStreamer для VideoFile (РЕКОМЕНДУЕТСЯ)

**Описание**: Переключение всех источников типа `VideoFile` на использование `VideoCaptureGStreamer` вместо `VideoCaptureOpencv`.

**Преимущества**:
- GStreamer имеет более надежную архитектуру для работы с файлами
- Поддержка циклического воспроизведения через `loop` параметр в pipeline
- Лучшая обработка ошибок и таймаутов
- Меньше проблем с многопоточностью

**Недостатки**:
- Требует наличия GStreamer в системе
- Несколько более сложная конфигурация pipeline

**Реализация**:
```json
{
    "type": "VideoCaptureGStreamer",
    "source": "VideoFile",
    "camera": "/path/to/video.mp4",
    "loop_play": true
}
```

**Статус**: ✅ Готов к использованию (модуль `VideoCaptureGStreamer` уже реализован)

---

### Вариант 2: Autoclose + внешний рестарт процесса

**Описание**: Использование механизма `autoclose` контроллера для автоматического перезапуска процесса при обнаружении проблем.

**Преимущества**:
- Не требует изменений в модуле захвата
- Простое решение для production окружений
- Полная изоляция проблемных состояний

**Недостатки**:
- Потеря состояния между рестартами
- Возможные задержки при перезапуске
- Не решает проблему на уровне захвата

**Реализация**:
```json
{
    "controller": {
        "autoclose": true,
        "auto_restart": true
    }
}
```

**Статус**: ⚠️ Требует настройки механизма детекции проблем

---

### Вариант 3: Отдельный процесс на источник

**Описание**: Запуск каждого источника видео в отдельном процессе Python с межпроцессной коммуникацией через очереди.

**Преимущества**:
- Полная изоляция проблемных источников
- Краш одного источника не влияет на другие
- Возможность независимого перезапуска источников

**Недостатки**:
- Значительные архитектурные изменения
- Увеличение сложности и overhead межпроцессной коммуникации
- Требует рефакторинга всей системы захвата

**Статус**: ❌ Не реализовано, требует значительной разработки

---

## Рекомендация

**Использовать Вариант 1 (GStreamer для VideoFile)** как наиболее надежное и готовое решение.

Для источников типа `VideoFile` с `loop_play=True` рекомендуется использовать `VideoCaptureGStreamer` вместо `VideoCaptureOpencv`.
