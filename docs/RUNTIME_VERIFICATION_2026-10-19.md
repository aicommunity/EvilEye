# Проверки на сервере 2026-10-19: обрыв RTSP, тревога в браузере, сравнение с main

Сервер `user-X99` (RTX 3060, Python 3.10, глобальное окружение), ветка `plugin_support` на коммите, указанном в
истории git, и `main` (`b18f81e`). Скрипты лежат в `scripts/`, их можно повторить.

## 1. Обрыв и восстановление RTSP (`scripts/rtsp_disconnect_check.py`)

Ролик 2688×1520 H.264 публикуется `cvlc`, EvilEye запускается без GUI, поток останавливается на 25 с и
поднимается снова. Проверяется: сообщение об обрыве, автоматическое переподключение, отсутствие постоянного сбоя,
сброс `degraded` после окна, чистое завершение.

| Бэкенд | Обрыв виден | Переподключение само | Постоянный сбой | `degraded` сброшен | Завершение чистое |
| --- | --- | --- | --- | --- | --- |
| GStreamer | да (`disconnect_count=1`) | да (`reconnect_count=1`) | нет | да | да |
| OpenCV (FFmpeg) | да | да | нет | да | да |

Особенности стенда: VLC отвечает 500 на `DESCRIBE`, пока не разобрал файл (около 5 с), поэтому клиентов нельзя
пускать раньше; VLC отдаёт только UDP. Живые камеры отключать нельзя, поэтому эта проверка идёт на потоке `cvlc`.

Найдено и исправлено по ходу:

- `SourceModuleAdapter` терял ключ `type` у capture-бэкендов: источник `VideoCaptureGStreamer` запускался через
  OpenCV и падал при `apiPreference=CAP_GSTREAMER` на OpenCV без GStreamer.

## 2. Тревога в браузере (`scripts/alarm_browser_setup.py`, `scripts/alarm_browser_check.py`)

Изолированный сайт с тремя тестовыми пользователями; `hardhat_1cam.json` с RT-DETR на ролике с людьми и
расписанием тревог на весь день; запуск через API «Runs», как в эксплуатации. Playwright входит через форму и
открывает «События».

| Пользователь | Права | Видит тревоги `Cam1` | Видит чужие события |
| --- | --- | --- | --- |
| `e2e_admin` | администратор | да | да |
| `e2e_cam1` | только `Cam1` | да | нет |
| `e2e_nocam` | без камер | нет | нет |

Найдено и исправлено по ходу:

- JSON-адаптер тревог расписания падал на каждой тревоге (`img_detected`); дефект есть и в `main`.
- В журнале у тревог расписания и атрибутных событий источник показывался как `0`, а пользователь с доступом к
  `Cam1` не видел событий: имя камеры теперь берётся из конфигурации пайплайна.
- Гонка в `ItemModuleAdapter.is_ready` давала «readiness check failed» с пустым сообщением.

Не покрыто: у тревог расписания нет превью (колонка «Превью» пуста): событие не несёт кадров.

## 3. Сравнение с `main` (`scripts/runtime_compare.py`)

Одинаковый клип 60 с (901 кадр, 2688×1520, 15 к/с), одна камера, `ObjectDetectorYolo` (`yolo11m.pt`) и BoT-SORT,
остальное из `hardhat_1cam.json`. Источник идёт в реальном времени, поэтому время обработки одинаково (72 и 77 с,
из них 60 с клип); сравнивается доля кадров, дошедших до выхода трекера (`EVILEYE_PERF_DIAG`, счётчик новых
кадров), по 3 прогона:

| Вариант | В детектор | Из трекера | Потери |
| --- | --- | --- | --- |
| `main` | 99,9–100% | 92,3–92,6% | 7,4–7,7% |
| ветка, по умолчанию | 100% | 82,7–83,0% | 17,0–17,3% |
| ветка, `queue_size=32` у детектора и трекера | 100% | 85,0–85,7% | 14,3–15,0% |
| ветка, детектор и трекер в `thread` | 99,9–100% | 76,8–76,9% | 23,1–23,2% |

Счётчики очередей ветки в конце прогона: детектор отбросил 60–62 кадра, трекер 90–91.

Вывод: на этой нагрузке ветка теряет на ~10 п.п. кадров больше, чем `main`. Размер очереди объясняет лишь малую
часть, режим `process` не причина (`thread` хуже). Причина не установлена; следующий шаг — профиль по стадиям
(`EVILEYE_PIPELINE_TIMELINE=1`), копирование кадра в shared memory на каждой стадии (см. `TECH_DEBT.md`,
TD-PS-D2) и стоимость пикла входного элемента 2688×1520. Целевые FPS, p95 и допустимую долю потерь по-прежнему
нужно зафиксировать (см. `PLUGIN_MIGRATION_COMPLETION_PLAN.md`).
